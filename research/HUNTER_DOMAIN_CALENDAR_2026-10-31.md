## Reproduction (exact source, mocked evidence; no actual upstream incident asserted)

Baseline `assessDomainAge` accepted an impossible `2026-02-30` event as normalized `2026-03-02`, reporting `recent_registration` with age 1 day at 2026-03-03. A future event `2026-03-04` returned `recent_registration` with age -1 day. These cases violate source-date integrity. The corrected decision requires `human_review` with `REGISTRATION_DATE_UNAVAILABLE` or `REGISTRATION_DATE_IN_FUTURE`. Legitimate 2024 leap day, same-day 0 age, older age and ISO RDAP timestamps remain compatible. Pre-commit isolated V8 execution of the exact fetched source and patch: 4 targeted before/after verdicts passed; this is not a substitute for GitHub's Node CI.

## Run 3: RFC 3339 instant fidelity + malformed timestamp rejection (2026-10-31 ET)

**Ownership:** continued existing unmerged Hunter draft PR #68 on its existing `hunter/domain-registration-calendar-20261031-r2` branch, not a competing PR. **Additional reproduced source defect:** `dateOnlyMs` sliced only the first ten characters from the source `eventDate`. With a registration at `2026-03-03T23:45:00-05:00`, it assigned **March 3** instead of the actual UTC day **March 4**; with `2026-03-03T00:30:00+14:00`, it assigned **March 3** instead of **March 2**. On 2026-03-03T23:59:00Z this first case was incorrectly `recent_registration` rather than `human_review` for a future UTC date. Any string beginning with `YYYY-MM-DD`, such as `2026-03-03not-really-a-date` or invalid `T99:99:99Z`, could also be classified as historical evidence. Verified by running the exact fetched prior decision.js through the isolated V8 execution engine: 10 named inputs, two full decision controls; no live registry incidents claimed.

**Standard and choice:** RDAP [RFC 9083 Section 4.5](https://www.rfc-editor.org/rfc/rfc9083.html#section-4.5) specifies `eventDate` as an actual event time; [RFC 3339 Section 5.6](https://www.rfc-editor.org/rfc/rfc3339.html#section-5.6) specifies explicit UTC offsets and time grammar. Rechecked pinned Luxon 3.7.2 MIT LICENSE and zero runtime dependencies, and Temporal polyfill 0.5.1 ISC LICENSE with JSBI dependency; both are maintained/not archived per GitHub metadata. Original native Date-based validation is ~20 lines, avoids introducing dependencies and transitive license/advisory risk. No code copied and no lockfile changes; same original-code/no-NOTICE conclusion.

**Change:** accept full valid RFC 3339 date-times and existing bare YYYY-MM-DD test contract; validate calendar, time, and offset; convert complete timestamp to the **UTC** day before threshold/future-day checks. Reject unrecognized suffixes, invalid clock fields and non-UTC-less timestamps conservatively as `REGISTRATION_DATE_UNAVAILABLE`. Valid leap dates, UTC Z, lower-case delimiters, positive/negative offsets and bare dates are covered. For leap-second `:60` inputs, native JS Date.parse does not represent the instant; fail closed to human review rather than inventing a date. Time-of-day future events *within* the same UTC day remain classified at day resolution per the existing product contract, a documented residual limitation.

Three new Node regression tests cover offset rollover, future-day decisions and malformed strings.
